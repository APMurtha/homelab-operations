# Owner authorization in one submission

Issue #42 demonstrated the deployed path. GitHub recorded the owner's ready-label event, an exact digest approval and a report with five running states. The challenge remains available for ordinary operations issues. A scheduled client that checks hourly can miss a five-minute challenge. The draft adds a second way to express consent using **one owner-authenticated GitHub comment**. Bag-End can discover it on its next tick. Issuance and result retrieval have separate lifetimes. [Issue #42 report](https://github.com/APMurtha/homelab-operations/issues/42#issuecomment-7112661813)

## Issuance and verification

A trusted owner device verifies the pre-enrolled inbox and current main revision, constructs the exact bounded task, generates 32 random nonce bytes, and asks an existing independent Ed25519 SSH signer to sign the canonical grant. The signed bytes are UTF-8 sorted-key compact JSON. They include protocol namespace, repository name and numeric ID, owner ID, inbox number and immutable ID, label ID and immutable enrollment event ID, nonce, issuance time, the complete operations-v1 task and its canonical SHA-256. Task fields bind the target, installed SSH host-key fingerprint, ordered observations, base SHA, expiry and time/byte/attempt limits. The issuer stores its signed intent in an exclusively created 0600 file, syncs it and its directory, then makes exactly one comment POST. Preflight GETs and read-only GraphQL queries do not create a challenge. A failed or ambiguous POST leaves the intent for reconciliation. Use the same intent path for the same requested action.

With an owner-controlled policy, known_hosts, task template and signer already available, the proposed owner entry point is:

```sh
python3 -IB submit_operations.py --policy inbox.json --known-hosts known_hosts \
  --task task-template.json --ttl-seconds 300 --identity /path/to/existing-owner-signing-identity \
  --receipt /private/directory/unique-task.intent
```

Review the task on the trusted device before invoking this command. The signer must stay outside connector, supervisor and model access. A connector that can ask the signer to sign arbitrary bytes is equivalent to possessing it. The helper prints the submission comment ID. After a timeout, match the saved body/nonce against owner comments on the enrolled issue before deciding whether another submission is appropriate. The signed envelope is temporarily reusable within its bound inbox until consumed, revoked or expired. Protect the saved intent accordingly. [OpenSSH signature operations](https://man.openbsd.org/ssh-keygen.1)

The optional Bag-End entry point uses the same collector, host pin checks, reply validator, attempt accounting, report reconciliation and terminal checkpoints as operations-v1. It runs separately from the existing engineering and fallback ticks, with its own SQLite directory and nonblocking lock. Neither existing timer nor workflow calls the new entry point. When separately invoked, it requires both SAMWISE_OPERATIONS_V1 and SAMWISE_OPERATIONS_SINGLE to equal enabled.

Bag-End pins its authenticated API client to github.com. It checks the control account and repository numeric IDs and current main SHA, the open owner-authored inbox, exact unedited marker body, current label ID and the original owner-attributed label event. Closure, reopening, transfer, unlabel/relabel, or marker edits invalidate the enrollment. Each grant requires the exact owner REST comment, matching GraphQL node and issue/repository, matching created time and body, and null lastEditedAt. The signed grant must verify under the independently enrolled public key and SSH signature namespace. Server creation must fall between issuance and expiry, the clock must still be inside a maximum 300-second grant, and the inbox epoch must predate issuance. The verifier rechecks before access and publication, including after claim. Only the private grant checkpoint binds the immutable submission comment ID; GitHub assigns that ID after submission. The signature binds the inbox and unique nonce before submission.

Read-only schema verification against #42 found issue and comment IDs above signed 32-bit range. GitHub's GraphQL fullDatabaseId returned a decimal string matching each REST integer. REST updated_at equality alone cannot exclude same-second edits. GitHub's node edit metadata supplies the additional check. [GraphQL IssueComment](https://docs.github.com/en/graphql/reference/objects#issuecomment), [issue comments REST API](https://docs.github.com/en/rest/issues/comments)

## Failure and threat model

| Condition | Enforcement and consequence |
| --- | --- |
| Forged body, copied signature, compromised connector | An owner-named field, bot attribution, label or authenticated owner comment alone cannot authorize. Changing any signed context, task or nonce invalidates the signature. A copied valid grant can authorize only the identical action within its original inbox and time window. |
| Duplicate, concurrent or competing claims | A SQLite transaction inserts the unique nonce, unique submission, initial task and claim receipt together. A process lock serializes the signed poll. Reposts cannot receive another attempt or report. Keep the nonce ledger across restarts, upgrades and rollback. |
| Edit, label race, source deletion or signer rotation | Fetch fresh provider evidence at checkpoints and compare the original proof, including comment ID, body hash, event and signer. Missing or changed proof prevents further authorization. Rotating/removing the policy withdraws pending grants at the next recheck. Bindings never follow an issue transfer or a replacement label epoch. |
| Cancellation | Post an owner comment containing exactly `cancel samwise-operations-single-v1 <64-lowercase-hex-nonce>` in the enrolled inbox. A seen cancellation leaves a permanent private tombstone, even if the comment is later deleted. A foreign actor cannot revoke. Closing the inbox or removing its label revokes the epoch. Deleting the original grant prevents its revalidation, but deletion alone cannot revoke an unseen signed copy. Use nonce cancellation. |
| Crash or lost POST response | The read attempt is consumed before SSH. A single-attempt grant cannot run twice after a crash. A validated result resumes at publication. A saved report intent reconciles the exact existing owner report; it never retries an uncertain report POST. |
| Clock, queue, GitHub or storage failure | Expired tasks do not run. Synchronize issuer and supervisor clocks. Pagination overflow and provider ambiguity fail closed. The signed client limits each tick to 64 GitHub API requests. High load, outages or rate limits may prevent completion within five minutes. Deleting or rolling back the nonce database invalidates the replay guarantee; withdraw the enrollment and wait out outstanding grants before recovery. |
| Concurrent withdrawal | An already-started read can finish inside its bounds. GitHub supplies no atomic compare-and-post that binds label state/cancellation to a simultaneous report write. A cancellation created and deleted entirely between observations is unknowable. The corresponding exposure exists in the challenge workflow. |
| Compromised signer or control plane | A connector holding the owner's GitHub token still lacks signing authority. A signer alone lacks the required GitHub actor. Compromise of both, the verifier host, or GitHub's authenticated provenance exceeds this trust model. An owner-token holder can interfere with GitHub availability or post an imitation report. Use the supervisor's private receipt for independent report attribution. |

## Result delivery investigation

The durable result remains an issue comment with a submission ID. An assistant can fetch the completed report later, after the grant expires, without another collection. The existing hourly automation could perform that retrieval where configured. It is unsuitable for a five-minute approval round trip.

| Option | Actual recipient and constraints |
| --- | --- |
| Existing GitHub subscription | GitHub can notify a subscribed person's inbox or email, subject to account settings and self-authored activity. Verify with the intended recipient. This requires no new receiver in Samwise. [GitHub notifications](https://docs.github.com/en/subscriptions-and-notifications/concepts/about-notifications) |
| GitHub Actions issue_comment | A workflow on the default branch can react to comment creation. A future design must distinguish result comments from submissions, prevent loops, verify report provenance and avoid running comment-controlled commands. It would still need an authorized destination for delivery. [Actions event reference](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#issue_comment) |
| GitHub webhook or App | Push to a separately operated HTTPS receiver would require a reachable endpoint, event subscription, secret/signature verification, delivery-ID deduplication, retry handling and retention review. None was configured or exercised. [Webhook delivery validation](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries) |

No supported unsolicited GitHub-to-existing-ChatGPT-conversation delivery path was demonstrated. Neither event-driven result delivery nor external callbacks are included in this implementation.

## Deployment proposal — separate owner decision

1. Review the branch, negative cases, GitHub provenance and signer independence. Identify an **existing** owner-controlled signing-capable Ed25519 identity accessible only to a trusted issuer. Verify its public fingerprint independently. The read-only GitHub public SSH-signing and GPG-key listings for this owner both returned zero; those listings cannot establish availability of a separate offline signer. No enrollment is feasible until an eligible existing signer is confirmed. Never substitute a service, host, deployment or collector key. If no such signer is available, keep the challenge path.
2. Under separate authorization, establish one owner-authored inbox with exact body `Samwise operations single-submission inbox v1` and one owner application of the existing operations-ready label. Independently record the issue number and REST ID, label ID and original label-event ID. Confirm GraphQL read access and the existing issue-comment permission with the intended identity. A named repository alone is insufficient.
3. Pin /etc/samwise/operations-v1/single-submission.json under root-owned non-writable ancestors. It contains exactly `issue`, `issue_id`, `label_id`, `event` (positive integers) and `key` (one public ssh-ed25519 key). Verify hashes on the dedicated operations checkout. Keep the signer off Bag-End. Protect the new 0700 state directory, use an unprivileged oneshot and the existing restricted operations access. The candidate entry point is `python3 -IB single_submission.py --state /absolute/private/ops-state`. Keep both enable gates off until approval. Verify rate budget, maximum wall time, clock sync and sufficient isolation from existing ticks before approving a schedule. Limit the pilot to one pending grant at a time.
4. Rehearse a synthetic signed read, cancellation, expiry and restart. Only with a separate live grant, submit a five-minute, one-attempt relay-only request and verify one read and one report. Inspect the legacy challenge and engineering paths independently. Configure any notification pilot separately with its intended recipient.
5. To withdraw, stop only the optional signed tick, clear its enable gate and withdraw the inbox epoch. Preserve its SQLite state and receipts. Verify the existing challenge timer and engineering workflow continue. No production activation, credentials, permissions, callbacks or inbox provisioning are part of the draft.
