# `anduin` OPNsense API access review

Status: **PROPOSED**, 2026-11-02. No account, API key, connector or authenticated request was created. The installed OPNsense version and its local API/ACL files have **not** been read. This matrix uses the current upstream OPNsense API reference and ACL source; confirm every privilege identifier and endpoint against the version installed on `anduin` before granting access. The [migration plan](udm-pro-max-migration.md) records the verified TLS transport check.

Installed-version gate: an authorized read-only UI/console session must record the OPNsense version and compare the local ACL definitions under `/usr/local/opnsense/mvc/app/models/OPNsense/{Core,Interfaces,Firewall,Kea}/ACL/ACL.xml` with this matrix. Check **System → Access → Privileges** and the proposed user's Effective Privileges in the installed UI. The web documentation is not proof of what `anduin` runs.

## Proposed endpoint and privilege matrix

Paths are relative to `https://10.10.10.1`. These are *candidate* exact GET paths for a future connector. `get_item/<id>` calls, if needed, require a validated identifier from an approved list result. Prefer `get` and `search_*` for bounded inventory. Do not infer that a `GET` is safe solely from its HTTP verb: the upstream API reference lists some mutation-named commands as GET. The ACL privileges below grant path families, potentially including writes; the connector must independently enforce a narrow read allowlist.

| Runtime interface IP/link state | `/api/interfaces/overview/interfaces_info` | Status: Interfaces (`page-status-interfaces`) | Runtime addresses/status, distinct from saved configuration; exclude reload/release actions. |

## Smallest proposed privilege set

For the **first API pass**, propose the exact ACL IDs: `user-config-readonly` (System: Deny config write), `page-interfaces-assignnetworkports`, `page-status-interfaces`, `page-interfaces-vlan-edit`, `page-interfaces-lagg-edit`, `page-filter-api`, `page-firewall-aliases`, `page-firewall-nat-portforward-edit`, `page-filter-snat-api`, `page-system-gateways`, `page-system-staticroutes`, and `page-dhcp-kea-v4`. Add `page-firewall-nat-1-1-edit`, `page-firewall-nat-npt`, or `page-dhcp-kea-v6` only after confirming those features are configured. Do not grant `page-all`, user management, backup/restore, firmware, service control, VPN write privileges, or broad diagnostic tools to this discovery account. The purpose is configuration inventory; do not grant leases/logs unless a separate review shows they are needed.

**Server-side read-only is not guaranteed by these grants alone.** OPNsense's `user-config-readonly` deny privilege was affected by API write bypasses in versions through 26.7 and patched in 26.7.1, according to the [official advisory](https://github.com/opnsense/core/security/advisories/GHSA-vw8q-pqq7-2q7v). Confirm `anduin`'s version and installed ACLs before creating the account. Even on a patched version, the page privileges cover broader URL patterns than the connector allowlist. The account should have no shell and no administrative group membership. Verify its Effective Privileges in the local OPNsense UI, then test only approved reads. Account/key creation is a production configuration change requiring separate authorization.

## Areas requiring alternative read-only collection

- **Legacy/interface firewall rules and true rule order:** The [Firewall API reference](https://docs.opnsense.org/development/api/core/firewall.html) explicitly says rules outside its automation UI are not returned. The [firewall manual](https://docs.opnsense.org/manual/firewall.html) describes modern MVC and legacy rules as separate implementations. Inspect the installed UI with an authorized read-only session or obtain an operator-reviewed, private redacted configuration snapshot. Include floating/interface rules, generated rules and observed behavior; no API-only completeness claim.
- **Legacy WAN/interface fields and DHCP options:** The [interface manual](https://docs.opnsense.org/manual/interfaces.html) notes legacy advanced/file-based settings may not appear in the MVC/API view. Compare its read-only legacy page with assignment API and runtime overview. Never save from either page during discovery.
- **Legacy/automatic outbound NAT and effective PF state:** Compare the installed NAT UI and runtime rules via an authorized read-only shell/console session or reviewed private snapshot. Do not use a broad config export in the connector or commit raw output.
- **Actual MGMT tagging and switch path:** OPNsense interface/VLAN/LAGG configuration cannot prove UniFi switch port native/tagged profiles or physical cables. Cross-check UniFi Network port configuration and a physical port map.
- **Full effective segmentation:** Configured rules do not prove behavior, especially across IPv6. Plan later bounded client tests of allowed and denied flows, with agreed endpoints, after the configuration inventory.

## Endpoint-specific connector design (no code installed)

1. Bind the connector to Andrew / `andrew-network` and exactly `https://10.10.10.1`; use `~/.config/nest/certs/anduin.pem` as the CA file for this target only. Keep certificate chain **and IP hostname** verification enabled. Refuse redirects, proxy inheritance, alternate hosts/ports and URL overrides.
2. Use OPNsense's API key/secret HTTP Basic authentication from a dedicated account. Per NEST `connect-home-service`, collect each secret through a hidden local prompt into the selected person's OS credential store (or a private mode-600 file under the selected binding if that is the reviewed local backend). Never accept secrets as command arguments or environment variables, print them, or place them in Git. Do not reuse the UniFi key or another person's binding.
3. Expose named read operations only. Each maps to one exact path/method from the reviewed list; no generic URL tool, POST/PUT/PATCH/DELETE, mutation-named GET, redirects or arbitrary query parameters. Validate UUIDs and bounded pagination. `get_item` requests require IDs obtained from a preceding approved read.
4. Cap response size and time; parse expected JSON; detect denied/incomplete responses. Keep raw payloads and public IPs private, redact secrets/identifiers in reports, and log only operation name, timestamp, HTTP status and redacted failure class. Fail closed on version/ACL mismatch, certificate error, unexpected content type or schema drift.
5. Review the installed API documentation/ACL and a dry-run request manifest before any authenticated call. First live test should be a single safe GET with a minimal privilege, followed by an explicit access/coverage report. No account, key, code or authenticated call is authorized by this design document.
